# 팀 개발 워크플로우 (Claude 협업 가이드)

> 우리 팀이 **Claude와 함께** 백엔드를 빠르고 안정적으로 개발하기 위한 규칙입니다.
> [BMAD 방법론](./bmad-method-방법론.md)의 핵심 아이디어를 우리 프로젝트(Spring Boot · TDD 미사용 · 팀 협업)에 맞게 다듬었습니다.
>
> 최종 수정: 2026-07-12

---

## 한 줄 요약

> **"계획을 문서로 먼저 쓰고 → 큰 일은 작게 쪼개고 → 팀이 같은 문서를 보고 → 큰 일만 꼼꼼히, 작은 일은 빠르게."**

우리는 **TDD(테스트 먼저 작성)를 쓰지 않는다.** 대신 **문서(계획)를 안전벨트로 삼는다.**
"시험지를 먼저 만들기"가 아니라 **"레시피를 먼저 자세히 적기"** 가 우리 방식이다.

---

## 왜 이렇게 하나 (배경)

Claude와 개발할 때 생기는 두 가지 고질병을 막기 위해서다.

1. **계획 불일치** — 요구사항이 애매하면 Claude가 엉뚱하게 구현한다.
2. **컨텍스트 손실** — 대화가 길어지면 Claude가 앞의 맥락을 잊는다.

→ 해결책은 **"잘 쓴 계획 문서"** 하나다. TDD가 아니어도 이 문제는 문서로 잡을 수 있다.

---

## 표준 개발 흐름

```
① 브레인스토밍  →  ② 계획 문서 작성  →  ③ Story 쪼개기  →  ④ 착수 전 점검  →  ⑤ 구현  →  ⑥ 코드 리뷰  →  ⑦ 커밋
```

| 단계 | 하는 일 | 도구 / 산출물 |
|------|---------|--------------|
| ① 브레인스토밍 | 무엇을·왜·엣지케이스를 대화로 정리 | `superpowers:brainstorming` |
| ② 계획 문서 | 구현 계획을 글로 작성 → **Git에 커밋** | `docs/superpowers/` 문서 |
| ③ Story 쪼개기 | 큰 기능을 작은 작업 단위로 분해 | 아래 "Story 쪼개기 규칙" |
| ④ 착수 전 점검 | "계획 다 됐지?" 게이트 체크 | 아래 "착수 전 체크리스트" |
| ⑤ 구현 | 계획대로 수직 슬라이스로 구현 | Claude 코딩 |
| ⑥ 코드 리뷰 | 안전망 (TDD 대체) | `/code-review` |
| ⑦ 커밋 | 컨벤션 준수 커밋 | `.claude/skills/git-commit` |

## 핵심 규칙 4가지

### 1. Story는 "Claude가 한 번에 기억할 수 있는 크기"로 쪼갠다
- Claude는 컨텍스트 창(기억 서랍)이 한정돼 있다. 너무 큰 일을 통째로 시키면 앞부분을 잊는다.
- ❌ "회원가입 기능 전부 만들어줘"
- ✅ "이메일 중복 검사 API 하나만 만들어줘" → "비밀번호 암호화 로직 추가" → ...
- 기준: **하나의 Story = 하나의 완결된 구현 단위** (한 세션에 끝낼 수 있는 크기).

### 2. 계획 문서는 반드시 Git에 커밋한다 (세션 간 정렬)
- 팀원 A의 Claude 세션과 팀원 B의 세션은 **서로의 대화를 볼 수 없다.**
- 계획·PRD·아키텍처 결정을 **Git 문서로 남겨야** 모두가 같은 기준으로 움직인다.
- `docs/` 폴더에 기능별 계획 문서를 두고, 각자 Claude에게 해당 문서를 참조시킨다.

### 3. 착수 전에 한 번 멈춰서 점검한다 (게이트)
코드를 만들기 **시작하기 전에** 아래를 확인한다.
- [ ] 무엇을 만드는지 한 문장으로 말할 수 있는가?
- [ ] 요구사항(입력/출력/예외)이 문서에 적혀 있는가?
- [ ] 기존 코드/컨벤션과 충돌하지 않는가?
- [ ] 이 Story가 컨텍스트 창 안에 들어가는 크기인가?

### 4. 일의 크기에 따라 힘을 조절한다 (과잉 프로세스 금지)
BMAD를 **모든 작업에 다 적용하면 오히려 느려진다.**

| 작업 종류 | 방식 |
|-----------|------|
| 🏗️ 크고 복잡한 새 기능 (예: 결제, 인증 시스템) | 풀 사이클 (①~⑦ 전부) |
| 🔧 작고 간단한 수정 (예: 필드 추가, 버그 픽스) | 경량 경로 (② 계획 생략, 바로 구현 → 리뷰) |

> ⚠️ 소규모 변경까지 전체 사이클을 강제하지 말 것. 판단은 "이거 나중에 되돌리기 어렵나?"로.

## 테스트 정책 (TDD 대신)

- **TDD(테스트 먼저) 금지.** 스펙이 흔들리는 단계에 테스트를 못박으면 테스트·구현을 둘 다 뜯어고쳐야 해서 느려진다.
- 대신 **구현이 안정된 뒤**, **핵심 경로만** 통합 테스트를 작성한다.
  - ✅ 통합/API 테스트 (`@SpringBootTest` + MockMvc) — 결제·인증·공통코드 등 깨지면 치명적인 경로
  - ❌ 반복적인 CRUD 유닛 테스트 — 생략
- **안전망의 주력은 테스트가 아니라 `/code-review`(Claude 리뷰) + 사람 리뷰다.**

## 협업 시 지켜야 할 습관

| 습관 | 이유 |
|------|------|
| **작은 PR로 자주 올린다** | 리뷰가 쉽고 충돌·디버깅 폭발을 막는다 |
| **한 세션 = 한 기능** | 컨텍스트 오염 방지. 기능 끝나면 새 세션 시작 |
| **수직 슬라이스로 개발** (Controller→Service→Repository 한 기능 끝까지) | 레이어별 병렬 개발은 통합 시점에 충돌한다 |
| **컨벤션은 CLAUDE.md·docs에 고정** | Claude가 매번 일관되게 동작한다 |

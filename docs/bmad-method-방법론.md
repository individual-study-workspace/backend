## 1. BMAD 란?

**BMAD = Breakthrough Method of Agile AI-Driven Development**
(AI 주도 애자일 개발을 위한 혁신적 방법론)

단순히 "프롬프트 → 코드 → 끝"이 아니라, **문서를 가드레일(guide rail)** 로 삼아
AI가 컨텍스트를 잃지 않도록 강제하는 **구조화된 파이프라인**이다.

```
의도(Intent) → PRD → 아키텍처(Architecture) → 스펙(Spec) → 스토리(Story) → 코드(Code)
```

### 핵심 철학
- AI 개발의 두 가지 고질적 문제를 해결한다.
  1. **계획 불일치 (planning misalignment)** — 요구사항이 애매해서 AI가 엉뚱하게 구현
  2. **컨텍스트 손실 (context loss)** — 대화가 길어지면 AI가 초기 맥락을 잊음
- 프로젝트 시작부터 완료까지 **일관된 컨텍스트를 문서로 유지**한다.
- 핵심 통찰: **BMAD는 AI를 더 똑똑하게 만드는 게 아니라, 사람에게 요구사항 정의의 엄격함(rigor)을 강제한다.** 애매한 스펙을 AI가 마음대로 구현하는 것을 막는다.

## 2. 전문 에이전트 (역할 분담)

각 에이전트가 특정 도메인을 전담한다.

| 에이전트 | 역할 | 담당 업무 |
|---------|------|----------|
| **Mary** | Analyst (분석가) | 아이디어 구체화, 리서치 |
| **John** | PM (기획자) | PRD 작성, 요구사항 정의 |
| **Sally** | UX Designer | 사용자 경험 설계 |
| **Winston** | Architect | 기술 아키텍처 설계 |
| **Bob** | Scrum Master | 스프린트 계획, 스토리 파일 생성 |
| **Amelia** | Developer | 구현 (원문 기준 TDD 기반) |
| **Quinn** | QA | 테스트 자동화, 리뷰 |

> 크게 두 국면으로 묶인다.
> - **계획(Agentic Planning)**: 분석가·PM·아키텍트가 협업해 일관된 PRD·아키텍처 문서 생성 (사람이 검수하는 human-in-the-loop 포함)
> - **개발(Context-Engineered Development)**: 스크럼 마스터가 "무엇을·어떻게·왜"가 모두 담긴 **스토리 파일**을 만들고, 개발자와 QA가 동일한 컨텍스트로 작업

## 3. 4단계 워크플로우

| 단계 | 이름 | 산출물 / 활동 |
|------|------|--------------|
| **Phase 1** | 분석 (Analysis) | "누가·왜·무엇을·성공 지표"에 답하는 **1페이지 Product Brief** |
| **Phase 2** | 기획 (Planning) | **12단계 인터뷰**로 PRD 작성 → **13단계 체크리스트**로 명확성·측정가능성·추적성 검증 |
| **Phase 3** | 설계 (Solutioning) | 시스템 아키텍처 설계, PRD를 **Epic/Story로 분해**, **6개 차원 게이트 체크**(구현 준비 완료 검증) |
| **Phase 4** | 구현 (Implementation) | 스프린트 계획 → 완전한 컨텍스트를 담은 **스토리 파일 생성** → 스토리 파일만으로 코드 구현 |

## 4. 핵심 개념

### PRD (Product Requirements Document)
- **가장 중요한 산출물.** 비전, 성공 기준, 사용자 여정, 기능/비기능 요구사항 포함.
- 계획 단계의 공백을 여기서 미리 드러내 구현 단계의 예상치 못한 문제를 방지.

### Architecture Document
- 시스템 설계 결정을 기록하되 **트레이드오프를 명시적으로 설명**.

### Epic / Story / Task 트리
- PRD를 계층적으로 분해.
- 각 **Story는 AI 컨텍스트 윈도우 안에 들어가는 크기**이며, **하나의 완결된 구현 단위**를 나타냄.

### Story File (스토리 파일)
- 개발에 필요한 **모든 컨텍스트를 하나의 문서에 통합**.
- 개발자가 문서 하나만 보고 "무엇을·어떻게·왜"를 이해할 수 있음.
- 문서를 매개로 핸드오프하므로 AI 컨텍스트 손실을 방지.

### Document Sharding (문서 샤딩)
- 큰 문서를 **기능별 파일로 분할**해 토큰 사용을 최적화.
- 압축 요약본(distillation)이 파일들을 연결.

### Implementation Readiness Check (구현 준비 완료 검사)
- 코딩 시작 전 모든 문서가 정렬됐는지 검증하는 **6단계 게이트**.

### 기타 기술 요소
- **Codebase Flattener**: 전체 프로젝트를 AI 최적화 XML로 변환. `.gitignore` 자동 제외, 바이너리 파일 감지.
- **Expansion Packs**: 창작·비즈니스·교육·헬스케어 등 도메인별 확장 팩.

## 5. 설치 & 사용

```bash
# Node.js 20+ 필요
npx bmad-method install
```
- 업데이트 시 기존 커스터마이징 보존.
- **Claude Code, Cursor, GitHub Copilot** 에서 슬래시 커맨드로 호출.

## 6. 장단점

### 장점
- 계획 공백이 **초기에 드러남** → PRD 완성도가 구현 단계의 놀람을 방지.
- 구조화된 분해로 **일관된 결과** 산출.
- 문서 매개 핸드오프로 **AI 컨텍스트 손실 방지**.

### 단점
- PRD 작성에 **상당한 초기 시간** 소요.
- **작은 변경도 전체 사이클 재실행** 필요 → `quick-dev` 같은 우회책은 문서 드리프트(문서-코드 불일치) 유발.
- 기존 프로젝트에 적용하려면 **PRD를 역으로 리버스 엔지니어링**해야 함.

## 7. 우리 프로젝트 적용 관점 (참고)

- 본 저장소는 **CLAUDE.md에서 TDD 미채택**을 명시(빠른 개발 우선)한다. BMAD 원문의 Developer 에이전트(Amelia)는 TDD 기반이라고 소개되지만, **BMAD의 핵심 가치는 TDD가 아니라 "문서(PRD·스토리)를 가드레일로 삼는 것"** 이므로 TDD 없이도 채택 가능하다.
- 이미 사용 중인 `superpowers`의 **brainstorm → plan → execute** 흐름과 철학이 동일하다(계획 문서로 컨텍스트를 고정). BMAD의 **Story 단위 분해**와 **문서 샤딩** 개념을 팀 협업에 부분 도입하면 좋다.
- **팀 + Claude** 환경에서 유용한 요소: ① Story를 컨텍스트 윈도우 크기로 쪼개기, ② PRD/아키텍처 문서를 Git에 커밋해 세션 간 정렬, ③ 구현 준비 완료 게이트로 착수 전 합의.
- 주의: 소규모 변경까지 전체 사이클을 강제하면 오히려 느려진다. **신규 기능·복잡한 작업에만 풀 사이클, 소규모 수정은 경량 경로**로 운영하는 것이 현실적이다.
